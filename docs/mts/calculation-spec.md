# MTS Calculation Specification

## Overview and Purpose

The Management, Timesheet and Financial Reporting (MTS) module is the financial backbone of the Technical Inspection Management Platform. It translates inspection activities into billable work, manages rate cards and contract pricing, prevents over-billing on mixed contracts, and produces auditable financial statements.

All monetary calculations in MTS use `Decimal` arithmetic with a fixed precision of `numeric(18,4)` at the database level and `Decimal('0.0000')` in Python. Rounding is applied only at statement export and invoice boundaries, using `ROUND_HALF_UP` with the currency's standard decimal places.

This specification is a living document. Every formula change requires a version bump in `RateCard` and a corresponding `RateRevision` entry.

## Reference Structure

### Section I — Objects and Party Taxonomy (IOPTC)

| Entity | Description |
|--------|-------------|

| `Client` | External entity commissioning inspection services. |
| `Project` | Client-scoped engagement containing one or more contracts. |
| `Contract` | Binding agreement with a contract type: `person_day`, `fixed_visit`, `milestone`, `mixed`. |
| `ContractRevision` | Versioned change to a contract (scope, value, terms). |
| `RateCard` | Billing profile linked to a contract with effective dates. |
| `RateRevision` | Individual line item in a rate card (unit, amount, multipliers). |
| `InspectorProfile` | Employee or contractor who performs inspections. |
| `Assignment` | Proposed or confirmed link between a notification and an inspector. |
| `InspectionVisit` | Scheduled or completed physical inspection event. |
| `InspectionReport` | Signed technical report issued after a visit. |
| `Timesheet` | Monthly timesheet header for an inspector on a project. |
| `TimesheetEntry` | Daily line with hours, travel, overtime, and visit linkage. |
| `Expense` | Reimbursable out-of-pocket cost claimed by an inspector. |

| `AuditEvent` | Immutable log of every financial calculation change. |

### Section II — Inspectors

Inspector compensation is computed from `RateRevision` lines. The compensation engine considers:

- Base hours (`actual_hours` in `TimesheetEntry`)
- Travel hours (`travel_hours`) multiplied by `travel_multiplier`
- Waiting hours (`waiting_hours`) multiplied by `travel_multiplier` unless the contract specifies otherwise
- Overtime hours (`overtime_hours`) multiplied by `overtime_multiplier`
- Minimum chargeable unit (`min_chargeable_unit`) — rounds short days up to the minimum
- Night allowance, remote area allowance, and other region-specific adjustments stored as `RateRevision` lines with `unit` values of `night`, `remote_day`, etc.

For contractor inspectors, `employment_type = 'contractor'` triggers a separate `RateCard` lookup by `region` and `effective_date`. For employees, internal payroll is excluded from client billing and kept in a separate cost ledger.

### Section III — Review

Before a `FinancialStatement` reaches the `approved` state, it passes through:

1. **Line Review** — Each `FinancialStatementLine` is matched to a source document (`Assignment`, `TimesheetEntry`, `Expense`). Void or reversed documents must carry `audit_reference_id` pointing to the original.
2. **Duplicate Detection** — The system checks whether any `assignment_id`, `visit_id`, or `timesheet_entry_id` has already been referenced in an approved or sent statement for the same `project_id` and overlapping `period`.
3. **Manager Approval** — A `Finance Officer` or `General Manager` approves the draft statement. Approval is atomic; it sets `status = 'approved'` and records `approved_by_id` and `approved_at`.
4. **Lock** — Once approved, the period is immutable unless a `ContractRevision` or formal adjustment memo is issued. Locked periods are flagged with `locked_at`.

### Section IV — Numbering

All financial documents use controlled sequences:

| Document | Sequence Rule | Example |
|----------|---------------|---------|
| `RateCard` | `RC-{PROJECT_CODE}-{YYYYMM}-{SEQ}` | `RC-PRJ001-202609-0003` |
| `RateRevision` | `RC-{RATE_CARD_ID}-{SEQ}` | `RC-12-001` |
| `FinancialStatement` | `FS-{PROJECT_CODE}-{YYYYMM}-{SEQ}` | `FS-PRJ001-202609-0001` |
| `Invoice` | `INV-{CLIENT_CODE}-{YYYY}-{SEQ}` | `INV-CL001-2026-00042` |
| `Payment` | `PMT-{INVOICE_NUMBER}-{SEQ}` | `PMT-INV-CL001-2026-00042-001` |
| `Expense` | `EXP-{INSPECTOR_ID}-{YYYYMM}-{SEQ}` | `EXP-INS007-202609-0011` |

Sequences are generated by PostgreSQL sequences with application-level caching for offline resilience.

### Section V — Data

All financial figures are stored as `numeric(18,4)` in PostgreSQL. The backend uses `Decimal('0.0000')` for intermediate calculations and rounds only at display or export boundaries.

**Currency handling:**
- Every `RateCard` and `RateRevision` carries a `currency`.
- `FinancialStatement` and `Invoice` carry a `currency`.
- Multi-currency projects use a `base_currency` on `CompanySettings`; all conversions are recorded as `ExchangeRate` rows with `effective_date` and `source`.
- Conversion rates are never hard-coded; they must be imported or captured at transaction time.

**Effective dating:**
- `RateRevision.effective_date` is inclusive.
- If a rate changes mid-period, the engine splits the `FinancialStatementLine` into two rows, each using the applicable rate.
- Expired rates are retained; they are marked `is_active = false` but remain queryable for audit.

**Contract value guard:**
- `Project.contract_value` is the ceiling.
- `FinancialStatement.total_billable` for a project cannot exceed `Project.contract_value` minus the sum of all prior approved statements, unless a `ContractRevision` raises the ceiling.

### Section VI — Pricing

#### 6.1 Person-Day Model

```
billable_amount = Σ_entries (
    (actual_hours + (travel_hours * travel_multiplier) + (waiting_hours * travel_multiplier) + (overtime_hours * overtime_multiplier))
    × person_day_rate / standard_day_hours
)
```

- `standard_day_hours` defaults to 8.0 and is configurable per `RateCard`.
- If `actual_hours + travel_hours + waiting_hours < min_chargeable_unit`, the engine pads the day to `min_chargeable_unit`.
- Example: `min_chargeable_unit = 8.0`, `actual_hours = 6`, `travel_hours = 1`. Total before padding = 7. Padded to 8.

#### 6.2 Fixed-Visit Model

```
billable_amount = fixed_visit_rate × visit_count
```

- `visit_count` is the number of `InspectionVisit` records with `status = 'completed'` linked to an approved `Assignment`.
- If a visit is split into multiple days, it is still counted as one visit unless `ContractRevision` specifies otherwise.

#### 6.3 Milestone Model

```
billable_amount = milestone_rate × completed_milestones
```

- `completed_milestones` is derived from `InspectionReport.status = 'issued'` or a manual milestone tracker.
- Milestones are configured in the `ITP` or a dedicated `ProjectMilestone` table.
- Each milestone has a fixed rate. Partial milestones are not billable unless the contract specifies pro-rata rules.

#### 6.4 Mixed Model Safeguards

A `mixed` contract combines two or more models. The system enforces:

1. **Allocation Ratio Lock** — At contract signing, the parties agree on an allocation ratio (e.g., 70% person-day, 30% fixed-visit). This ratio is stored in `Contract.meta` as JSON and cannot exceed ±10% without a `ContractRevision`.
2. **Model Separation** — Each `FinancialStatementLine` is tagged with `billing_model`. The sum of person-day lines cannot exceed `contract_value × allocation_ratio.person_day`.
3. **Double-Billing Prevention** — Before inserting a `FinancialStatementLine`, the engine runs:

```sql
SELECT COUNT(*) FROM financial_statement_line fsl
JOIN financial_statement fs ON fs.id = fsl.financial_statement_id
WHERE fsl.source_id = :source_id
  AND fs.project_id = :project_id
  AND fs.status NOT IN ('void', 'draft')
  AND fsl.void = false
```

If count > 0, the insertion is rejected with `DuplicateBillingError`.

4. **Advance Hold** — If the client has paid an advance against a mixed contract, the advance is applied proportionally across models. The engine does not release the advance to a single model beyond its allocation.

### Section VII — Guide

#### 7.1 Reimbursable Expenses

Reimbursable expenses are claimed through the `Expense` model. Each expense is linked to a `Project` and optionally to an `Assignment`.

- Expenses are billable only when `Expense.is_billable = true` and the project is not `closed`.
- Supported expense types: `transport`, `accommodation`, `daily_allowance`, `courier`, `other`.
- `daily_allowance` rates are looked up from `RateRevision` with `unit = 'day'` and `rate_type = 'daily_allowance'`.
- Receipts are stored as attachments in object storage; the path is recorded in `Expense.receipt_path`.
- Expenses flow into `FinancialStatementLine` with `line_type = 'expense'`.

#### 7.2 Net Billable Amount

```
net_billable_amount = total_billable - adjustments - credits - advance_applied
```

- `adjustments` include write-offs, goodwill credits, and correction entries.
- `credits` are negative adjustments from previous over-billings.
- `advance_applied` is the portion of the client's advance applied to this statement.
- Net billable amount is the basis for tax calculation and invoice generation.

#### 7.3 Direct Project Cost

```
direct_project_cost = Σ(inspector_compensation + reimbursable_expenses + subcontractor_fees + direct_logistics)
```

- `inspector_compensation` is the internal cost of inspector time, looked up from the `RateRevision` with `billing_model = 'cost'` (internal cost card).
- `reimbursable_expenses` are actual out-of-pocket costs paid by the company.
- `subcontractor_fees` are third-party inspection fees passed through to the client or absorbed.
- `direct_logistics` includes travel booked by the company, not travel reimbursed to inspectors.

#### 7.4 Gross Project Profit

```
gross_project_profit = net_billable_amount - direct_project_cost
```

- Gross profit is calculated per project per financial period.
- Negative gross profit triggers an alert to the `General Manager` and `Finance Officer`.

#### 7.5 Gross Profit Margin

```
gross_profit_margin = (gross_project_profit / net_billable_amount) × 100
```

- If `net_billable_amount = 0`, margin is recorded as `NULL` and flagged as `zero_revenue` in `FinancialStatement.meta`.
- Target margin thresholds are stored in `CompanySettings` as `target_gross_margin_min` and `target_gross_margin_warning`.

### Financial Statement Structure

A `FinancialStatement` contains:

```
FinancialStatement
  ├── project_id
  ├── contract_id (nullable; if null, aggregates all active contracts for the project)
  ├── period_start
  ├── period_end
  ├── currency
  ├── status: draft | approved | sent | paid | partial | void
  ├── total_billable
  ├── total_invoiced (sum of all invoices against this statement)
  ├── current_amount (amount on the current draft invoice)
  ├── tax_amount
  ├── total_due
  ├── approved_by_id
  ├── approved_at
  └── locked_at

FinancialStatementLine
  ├── financial_statement_id
  ├── line_type: visit | timesheet | expense | adjustment | milestone | tax
  ├── source_id (FK to Assignment, TimesheetEntry, Expense, etc.)
  ├── billing_model
  ├── quantity
  ├── unit_rate
  ├── line_amount
  ├── currency
  ├── cost_amount (internal cost mapped to this line)
  ├── notes
  └── void
```

### Distinct Financial Concepts

| Concept | Definition |
|---------|-----------|
| **Contracted Value** | `Contract.total_value` at the time of signing. Subject to revision via `ContractRevision`. |
| **Billable Work** | Sum of `FinancialStatementLine.line_amount` for approved lines within a contract period. Represents work that *can* be invoiced. |
| **Invoiced Value** | Sum of `Invoice.total_amount` for invoices issued against a contract or project. Represents money formally requested from the client. |
| **Collected Payments** | Sum of `Payment.amount` with `status = 'settled'` linked to invoices for the contract. Represents cash in hand. |
| **Recognized Revenue** | Portion of `invoiced_value` recognized in the current accounting period based on the company's revenue recognition policy (typically percentage-of-completion or milestone-based). Stored in `FinancialStatement.recognized_revenue`. |

### Exports

#### PDF Export

- Uses a Django template rendered via WeasyPrint or a headless Chromium microservice.
- Layout: company header, client/project summary, statement period, line-item table, tax summary, totals, approval signatures.
- Bilingual: Persian (default) with English fallback based on `Client.preferred_language`.
- Digital signature: PDF is timestamped and the SHA-256 hash is stored in `AuditEvent`.

#### Excel Export

- Uses `openpyxl` or `xlsxwriter`.
- Sheets: (1) Summary, (2) Statement Lines, (3) Timesheet Detail, (4) Expense Detail, (5) Cost Reconciliation.
- Formulas are preserved in the workbook for finance review.
- Currency formatting follows the `currency` code; Jalali dates are formatted using `convertdate`.

#### CSV Export

- Single-sheet, UTF-8 BOM for Persian Excel compatibility.
- Columns: `statement_number`, `line_number`, `date`, `description`, `billing_model`, `quantity`, `unit_rate`, `line_amount`, `cost_amount`, `margin`.
- Used for import into legacy accounting software (e.g., *Sadad*, *TAPP*).

## Sample Calculation Walkthroughs

### Walkthrough 1 — Person-Day Contract

**Contract:** `C-2026-045` | Type: `person_day` | Currency: `USD` | Value: `150,000`
**RateCard:** `RC-PRJ001-202609-0002` | Standard day: 8 hours | Person-day rate: `1,200 USD`

Inspector `INS-007` works three days in September 2026:

| Day | Actual Hours | Travel Hours | Waiting Hours | Overtime Hours | Travel Mult | OT Mult | Notes |
|-----|--------------|--------------|---------------|----------------|-------------|---------|-------|
| 12 | 8.0 | 0.0 | 0.0 | 0.0 | 1.0 | 1.5 | Normal day |
| 13 | 6.0 | 1.0 | 0.5 | 0.0 | 1.0 | 1.5 | Short day |
| 14 | 0.0 | 0.0 | 0.0 | 0.0 | — | — | Travel only |

**Day 12:**
```
chargeable_units = (8.0 + 0.0*1.0 + 0.0*1.0) = 8.0
billable = 8.0 / 8.0 × 1,200 = 1,200 USD
```

**Day 13:**
```
raw_units = 6.0 + 1.0*1.0 + 0.5*1.0 = 7.5
min_chargeable_unit = 8.0
chargeable_units = 8.0 (padded)
billable = 8.0 / 8.0 × 1,200 = 1,200 USD
```

**Day 14:**
No work performed, no billable event. Travel hours alone do not generate a line unless an `Assignment` exists and the contract allows travel-only days.

**Monthly Total:**
```
total_billable = 1,200 + 1,200 = 2,400 USD
internal_cost = (8.0 + 7.5) × 450 (internal cost rate) = 6,975 USD
gross_profit = 2,400 - 6,975 = -4,575 USD
margin = NULL (zero revenue for this visit context)
```

Wait — the margin is negative because this inspector is underutilized relative to the internal cost rate. In production, the system flags this for the `Finance Officer`.

### Walkthrough 2 — Mixed Contract with Milestone and Person-Day

**Contract:** `C-2026-089` | Type: `mixed` | Currency: `EUR` | Value: `200,000`
**Allocation Ratio:** 60% person-day, 40% fixed-visit/milestone

**Person-Day Bucket (60% = 120,000 EUR):**
Inspector `INS-012` performs 5 days at `900 EUR/day`:
```
person_day_billable = 5 × 900 = 4,500 EUR
```

**Milestone Bucket (40% = 80,000 EUR):**
Milestone M3 (ITP Release) is completed and verified:
```
milestone_billable = 25,000 EUR
```

**Expenses:**
Travel and accommodation for 2 inspectors:
```
expense_billable = 3,200 EUR
```

**Statement Total:**
```
total_billable = 4,500 + 25,000 + 3,200 = 32,700 EUR
allocation_check_person_day = 120,000 / (200,000 / 30 days) ≈ 2,000 per day ceiling
cumulative_person_day_billable = 4,500 ≤ 2,000 × 5 = 10,000 → PASS
allocation_check_milestone = 80,000
cumulative_milestone_billable = 25,000 ≤ 80,000 → PASS
```

**Tax (9% VAT):**
```
tax_amount = 32,700 × 0.09 = 2,943 EUR
total_due = 35,643 EUR
```

**Internal Cost:**
```
inspector_cost = 5 × 650 = 3,250 EUR
expense_cost = 3,200 EUR
direct_cost = 6,450 EUR
gross_profit = 32,700 - 6,450 = 26,250 EUR
margin = 26,250 / 32,700 × 100 = 80.28%
```

### Walkthrough 3 — Double-Billing Prevention

Scenario: `InspectionVisit #VIS-2026-0045` was already included in `FinancialStatement FS-PRJ001-202609-0001`.

Attempt to create a new line referencing the same visit in `FS-PRJ001-202609-0002`:

```
SELECT COUNT(*) FROM financial_statement_line fsl
JOIN financial_statement fs ON fs.id = fsl.financial_statement_id
WHERE fsl.source_id = 45  -- InspectionVisit id
  AND fs.project_id = 1
  AND fs.status NOT IN ('void', 'draft')
  AND fsl.void = false
-- Returns 1 → DuplicateBillingError raised
```

Resolution: The system requires the user to either (a) void the original line (creating an audit trail), or (b) create an adjustment line in the current statement referencing the original line.
