# ADR-001: Architecture Selection

## Status
Accepted

## Date
2026-09-29

## Context

We need to build a commercial-grade Technical Inspection Management Platform for a single third-party inspection company. The system must support the full business lifecycle from client request to financial reporting, with Persian RTL as the default interface, Jalali/Gregorian dates, mixed contract billing, electronic signatures, and ISO 17020-aligned traceability.

We evaluated two primary architectural approaches:
- **A.** Standalone Django backend + React frontend
- **B.** Custom application built on Frappe/ERPNext

We also investigated ERPNext, OCA Field Service, Beveren FSM, OpenInspection, Django, and DRF as reference implementations or potential foundations.

## Decision

Adopt **Option A**: Standalone Django backend with a React frontend.

### Backend Stack
- **Framework:** Django 5.x LTS
- **API:** Django REST Framework
- **Database:** PostgreSQL 17
- **Cache / Broker:** Redis 7
- **Async Tasks:** Celery
- **Storage:** S3-compatible object storage (MinIO or AWS S3)
- **API Docs:** drf-spectacular (OpenAPI 3)
- **Testing:** pytest + pytest-django
- **Containerization:** Docker + Docker Compose

### Frontend Stack
- **Framework:** React 18 + TypeScript
- **Bundler:** Vite 6
- **State / Data:** TanStack Query v5 + Zustand
- **Forms:** React Hook Form + Zod
- **UI Library:** MUI v6 (RTL-tested) or Mantine v7
- **Dates:** dayjs + jalali-dayjs
- **Signatures:** react-signature-canvas
- **Maps / Scheduling:** react-big-calendar or custom calendar

### Infrastructure
- **Reverse Proxy:** Nginx
- **Process Manager:** Gunicorn (backend) + Nginx static serving
- **Secrets:** Environment variables (12-factor); no secrets in repo
- **Backups:** Scheduled pg_dump + storage sync
- **Monitoring:** Django health checks + optional Prometheus/Grafana

## Rationale

1. **License Safety:** The selected stack is permissively licensed (BSD, MIT). We avoid GPLv3 contamination that would require releasing proprietary inspection modules under the same license.
2. **Domain Fit:** Django's ORM, admin, and DRF serialization map cleanly to the normalized relational schema required for traceability. We can enforce object-level permissions and audit logging at the model and view layers.
3. **Localization Control:** A decoupled React frontend lets us implement Persian typography, RTL layout, and Jalali calendars without fighting backend template constraints.
4. **Operational Simplicity:** Docker Compose gives a single reproducible artifact for development, staging, and production. The same Compose file runs on an internal server or a VPS with only environment changes.
5. **Maintenance:** Django LTS and React have predictable release cycles and large talent pools. We are not betting on niche frameworks.
6. **Extensibility:** Modular Django apps (`clients`, `projects`, `inspections`, `reports`, `mts`, etc.) allow phased delivery. Each phase can be deployed independently.

## Consequences

- **Positive:** Full control over every layer; no vendor lock-in; clean separation of concerns.
- **Negative:** More initial scaffolding than a Frappe-based approach; we must build the admin UI and workflow engines ourselves rather than configuring Frappe's DocTypes.
- **Mitigation:** Reuse proven open-source libraries (DRF, Celery, MUI, TanStack Query) to avoid reinventing infrastructure. Follow the phased plan to deliver vertical slices before expanding horizontally.

## Alternatives Considered

### Frappe / ERPNext
Rejected because GPLv3 licensing conflicts with a commercial inspection module, and Frappe's DocType model is optimized for general ERP rather than highly regulated inspection workflows with ISO 17020 traceability requirements.

### OCA Field Service (Odoo)
Rejected because it is tightly coupled to Odoo's LGPLv3 ecosystem and lacks the specialized inspection reporting, signature binding, and Persian RTL depth required.
